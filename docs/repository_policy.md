# Research Repository Policy

## 1. 外部リポジトリ

実験対象の外部リポジトリは，特定のコミットに固定する。
最終的にはGit submoduleとして管理する。
元リポジトリのソースコードを研究用親リポジトリへ直接コピーしない。

## 2. 実験単位

各実験実行には一意のrun IDを付与する。
過去の実験結果は上書きしない。

## 3. 保存するデータ

- LLMへ実際に送信した入力
- プロンプト
- LLMの未加工応答
- 整形後の設計文書
- 再生成コード
- ビルドログ
- 直接テストログ
- 全テストログ
- 復元ログ
- メタデータ
- 最終判定

## 4. 保存しないデータ

- APIキー
- パスワード
- `.env`
- ビルド生成物
- Dockerイメージ
- モデル重み
- キャッシュ

## 5. LLM出力

LLMの未加工応答と，実際に評価したコードを別ファイルで保存する。
人間が修正した場合は，修正内容を必ず記録する。
最小実験では生成コードに対する修正を行わない。

## 6. 実験失敗

コンパイル失敗，テスト失敗，タイムアウトなども研究データとして保存する。
成功結果だけを選択して残してはならない。

BlockDequeの直接テストが実行時非終了となったことを受け，
以後の実験では各評価段階に固定タイムアウトを設定する．
configureは300秒，buildは600秒，direct_testは300秒，
full_testは600秒とする．タイムアウトはFAILとして記録し，
後続段階は未実行とする．また，評価コンテナを自動削除した後，
元ソースを復元する．
## 追加分析予定：コード再生成時の出力上限に関する感度分析

Echo-Web-Serverの`log`を対象とした主実験では，
`num_predict=8192`の上限に到達し，コード再生成結果が途中で終了した．
このため，生成結果のJSONが完結せず，生成ファイルの抽出，ビルド，
およびテストを実施できなかった．

主実験の結果は，固定した出力条件下での
`code_regeneration_output_truncation`によるFAILとして保持する．

全対象の主実験完了後，追加分析として出力上限を拡大した実験を行う．
追加分析では，主実験とは異なるrun_idを使用し，主実験結果を上書きしない．
生成回数は1回，再試行なし，自動修復なしの条件を維持する．

追加分析の目的は，次の二つを区別することである．

1. 設計文書からコードを正しく再生成できない失敗
2. コードを出力するためのトークン上限が不足したことによる失敗

追加分析では，少なくとも以下を確認する．

- コード再生成が`done_reason=stop`で完了するか
- 出力されたJSONを正常に解析できるか
- 全対象ファイルを抽出できるか
- configureおよびbuildに成功するか
- 直接テストおよび全体テストに成功するか

出力上限の候補は`num_predict=16384`とする．
ただし，追加分析開始前に値を確定し，実行後の事後的な変更は行わない．
