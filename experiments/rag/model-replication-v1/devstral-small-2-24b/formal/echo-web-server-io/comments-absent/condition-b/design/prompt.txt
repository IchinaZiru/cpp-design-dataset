std::size_t FileDescriptor::WriteTo(Buffer& buf) {
    const auto buf_bytes {buf.WritableBytes()};
    std::array<std::byte, 0x10000> ext_bytes;

                                                  
                                                              
                                                                  
                                         
    const std::array bufs {
        iovec {.iov_base = buf_bytes.data(), .iov_len = buf_bytes.size_bytes()},
        iovec {.iov_base = ext_bytes.data(), .iov_len = ext_bytes.size()}};

    const auto size {readv(read_, bufs.data(), bufs.size())};
    if (size < 0) {
        ThrowLastSystemError();
    } else if (size <= buf_bytes.size_bytes()) {
        buf.HasWritten(size);
    } else {
        buf.HasWritten(buf_bytes.size_bytes());
        buf.Append({ext_bytes.cbegin(),
                    ext_bytes.cbegin() + (size - buf_bytes.size_bytes())});
    }

    return size;
}

std::size_t FileDescriptor::ReadFrom(Buffer& buf) {
    const auto bytes {buf.ReadableBytes()};
    if (const auto size {write(write_, bytes.data(), bytes.size_bytes())};
        size >= 0) {
        buf.Retrieve(size);
        return size;
    } else {
        ThrowLastSystemError();
    }

# 汎用詳細設計知識 v4

## 目的

対象コードから、再実装に必要な実装上の事実を失わない詳細設計情報を生成する。
v3のクラス図・インターフェース詳細・シーケンス図・メソッド仕様・処理フロー・状態遷移・データ変換の観点は維持するが、単なる情報量の増加ではなく、再生成に必要な正確性を優先する。

## 共通記述規則

- 元コードと与えられた文脈から確認できる事実だけを記述する。
- 元コードにない機能、API、型、状態、初期値、例外、依存関係、制約を推測で追加しない。
- 確認できない情報は推測せず「確認不能」と記述する。
- ソースコード全文を複製しない。再実装に必要な事実を、表、短い式、疑似コード、図、自然言語へ変換して記述する。
- 識別子、型名、関数名、メソッド名、メンバ名、定数名、条件、演算子、数値は、再実装結果に影響する場合は元コードの表記と意味を保つ。
- 同じsymbolを複数の表・図で記述する場合、型、可視性、const、副作用、呼び出し先、状態更新を互いに矛盾させない。矛盾が生じる場合は元コードで確認できる事実を正とする。
- 対象に該当しない成果物は「該当なし」と簡潔な根拠を記述する。
- 図はMarkdown内のMermaidで記述することを推奨するが、図の形式より設計内容の正確性を優先する。

## 再実装忠実度の必須観点

### 1. 正確な定義

再実装に影響する `using`、`typedef`、`enum`、`concept`、`requires`、macro、定数、nested/base class、構造体フィールドについて、確認できる場合は名前だけでなく実体・値・構造を記述する。

ソース全文の引用は不要であり、例えば型別名は「型名 / 種別 / 実体」の表として記述してよい。

### 2. 直接依存インターフェースと利用方法

対象が直接利用する関数・メソッド・型について、確認できる範囲で以下を記述する。

- qualified name / namespace
- 引数名と型
- 戻り値型
- `const`、`noexcept`、`static`、`virtual`
- 参照・ポインタの区別
- 実際に渡す値や型変換
- 戻り値の消費方法
- 呼び出し順序

「Loggerを使う」「Memoryへ書く」のような抽象的記述だけで終わらせず、元コードから確認できる場合はどのAPIをどのように利用するかまで設計情報として残す。

### 3. 結果を決める式・具体値

次のような値や式が実装結果を決める場合、自然言語へ丸めず正確に保持する。

- 条件式、比較演算子、switch case
- bit位置、bit幅、mask、shift量、符号拡張
- byte数、サイズ単位、長さ制約
- 配列index、offset、アドレス増分
- loop境界、増分値
- literal、sentinel、default値、error code
- 文字列・改行・encodingなどの変換規則

関数本体全体を貼る必要はなく、表や短い式、疑似コードとして記述してよい。

### 4. 使用データ・更新データ

処理が参照・更新するデータについて、再実装に必要であれば具体的なアクセス対象を記述する。

- `object.member.submember` のような参照先
- 入力 / 出力 / 内部状態の区別
- 初期値と更新後の値
- 更新条件と更新順序
- コピー元 / コピー先
- データの所有権・寿命

### 5. 状態・副作用・不変条件

状態更新、所有権、寿命、lock範囲、wait predicate、notify、close、error contractなど、動作の正当性に必要な制約を記述する。

「副作用なし」と記述する場合は、メンバ・外部資源・出力引数・ログ・I/Oの変更が本当にないことを元コードから確認する。

## 完全再構築台帳

- full-file/module-file unitでは、ファイル先頭から末尾までを再構築できるように、include guardまたはpragma、すべてのincludeを綴りと順序を保って記録し、すべてのtop-level宣言を出現順に列挙する。
